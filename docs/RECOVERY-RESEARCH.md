# 从缺失画面恢复下注记录：研究与本次边界

## 结论

本次只扩大 **已有可信牌局内，同一条街、多名玩家纯跟注或弃牌** 的漏帧恢复。没有把任意中途画面改称完整历史，也没有把三个盲注数字直接当作本手已投入第三盲。

`PublicHandLedger` 仍从经过核对的强制下注开局开始；原有单次开池快照入口保持独立来源。新增例外仅放宽 `reconcile` 的“多名玩家付筹码即拒绝”条件，后续合法动作重放、唯一性、两帧确认和建议时效不变。

## 录像中的实际问题分组

以下是修改前 `reports/systemic-full-video-replay.json` 的历史基线。原始录像、截图和本地报告不随公共仓库分发，不能把这组私有样本的结果当作公开可独立复现的数据集。

240 帧中有 39 帧被识别为本人可操作，7 帧允许完整策略。其余 32 帧为：

| 分组 | 帧 | 数量 | 本次是否直接解决 |
| --- | --- | ---: | --- |
| 开局两帧确认中 | 0017–0018 | 2 | 保留确认要求 |
| 翻后新状态首次确认 | 0044、0060 | 2 | 保留确认要求 |
| T7 这一手失去早期记录 | 0119–0123、0129–0132、0136–0138、0144–0149 | 18 | 必须先恢复本手的早期开局，不能只看翻后画面补历史 |
| QQ 这一手多人全下后的翻前与翻后 | 0186、0203–0207、0213–0214、0219–0220 | 10 | 必须先建立本手记录并连续追踪；本次没有新增全下快照重建 |

只有 5 个本人操作帧处于翻前：0017–0020 和 0186。因此只扩大“轮到本人时的单开池快照”不会自动修复大多数失败帧。

更早的 0170–0172 帧是有用的多人跟注样本。顺时针 Core 座位的本街投入为 `[0, 0, 20, 50, 100, 0, 280, 280]`，Core 5 已弃牌，底池 730。已确认第三盲时，它可对应开池 280 后一人跟注；尚未确认第三盲时，它也可对应 UTG 先加到 100、下一人再加到 280、随后一人跟注。这两种解释不能只因其中一种超出恢复器能力就被删除。

这些手的早期本人第三盲标签读取属于另一个独立的画面识别修复。两项改动结合后的实际覆盖率，需要重新跑整段录像后报告，不能由以上分组直接推算。

## 主源给出的约束

PokerKit 将强制下注、当前街投入、剩余筹码、行动队列、上一笔足额加注增量分别维护；`complete_bet_or_raise_to` 的金额是本街总额，实际扣款是总额减本人已经投入的金额。短全下是否重新开放加注权还取决于之前是否已经行动，不能只凭底池和最大下注额恢复。[PokerKit 状态实现](https://raw.githubusercontent.com/uoftcprg/pokerkit/main/pokerkit/state.py)

PokerKit 的位置从小盲顺时针排列，强制下注与每条街最小下注额可分别配置。项目的 WPK 配置是翻前名义 100、后续街恢复 BB 50；直接将通用 `min_bet` 永久设成 100 并不等价。[PokerKit 游戏配置](https://pokerkit.readthedocs.io/en/stable/simulation.html)

PokerKit 的手牌历史加载是从初态按动作逐一重放；OpenSpiel 的 ACPC 适配层同样调用动作合法性检查再推进状态，并维护下注序列。这些组件可作为规则对照，并不自动补出 OCR 未看见的动作。[PokerKit 历史格式](https://pokerkit.readthedocs.io/en/stable/notation.html)、[OpenSpiel ACPC 实现](https://github.com/google-deepmind/open_spiel/blob/master/open_spiel/games/universal_poker/acpc_cpp/acpc_game.cc)

以下恢复边界是本项目根据这些规则作出的推导，不是上述项目自带的截图恢复算法。

## 本次实现的充分条件

设已有状态的最高下注额为 `B`。对于两帧之间有两名或更多玩家付出筹码的情况，只有同时满足以下条件才进入原有搜索：

1. 公共牌完全相同，没有换街。
2. 每个座位的剩余筹码、街投入和弃牌状态完整；原有弃牌不可撤销，筹码不可增加。
3. 每个座位的终点街投入不小于起点，且不超过 `B`。
4. 每个座位的筹码减少量，严格等于其街投入增加量。
5. 底池增加量严格等于所有玩家的筹码减少量之和。
6. 终点至少有两名未弃牌且仍持有筹码的玩家，保守排除全下或弃牌结束时未跟满加注被退款的边界。

在同一条街且无退款时，街投入单调增加。任何遗漏的加注都必须把至少一人的街投入提高到 `B` 以上；这与第 3 条矛盾。因此这个例外中不可能藏有新的加注。短筹码玩家可以封顶跟注：其实际投入不超过 `B`，不会改变最高下注额、上一笔足额加注或其他人的加注权。

这只是允许搜索的条件，不是直接宣布恢复成功。仍必须从原状态按实际行动顺序重放，匹配每个人的金额、弃牌、当前行动者及底池；所有合法解释必须得到相同状态和相同动作路径。达到状态数或动作深度预算就失败，不能把尚未搜到的解释当作不存在。未知行动者只用于内部记录，不能刷新建议。

## 必须保留的反例

- **第三盲与第一次自愿加注：** 同样的 `[20, 50, 100, 0…]` 可能是第三盲 100，也可能是普通 BB 50 下 UTG 加到 100。下一次最小加注分别可能是 200 与 150。
- **多人同额不等于单开池：** 在已完成的一轮下注中，所有人最终都投入 300，既可来自一次开到 300，也可来自开到 200 再加到 300。先前的加注增量与范围含义不同。
- **免费让牌：** 所有人跟到第三盲后，第三盲尚未行动和已经让牌的金额完全相同。没有行动者或换街证据时，不能凭金额选择其中一项。
- **未跟满部分退款：** 一人加到 200、其他深筹码弃牌、短筹码只跟满 100，退款后净投入可与仅跟到 100 相同。PokerKit 在收集下注时会清空街投入；画面上各字段独立刷新也不能作为“绝无退款”的证据。本次对只剩一名有筹码者的多付款跳帧保守拒绝。
- **跨街：** 街投入会归零，前一条街的加注可以被终点画面隐藏。本次例外不跨街。

## 未实施的更宽快照入口

可进一步研究完整、无全下的翻前快照，在每种仍可能的桌规下枚举 limp、call、fold 和单次开池。一个保守子集是：名义 bring-in 为 `B`，最高投入为 `B`（无加注），或 `2B ≤ M < 3B`。第二次足额加注最早达到 `3B`，所以这个子集可以排除被抹平的两次足额加注。原有“只有一名自愿付筹码者”的单开池入口可继续支持更大金额。

但未知 optional straddle 必须保留所有可能解释；`M ≥ 3B` 的多付款端点不能只枚举一次加注后宣布穷尽。还要保存路径候选，处理免费让牌、未识别行动者、开池者范围和多人调用栈。既有录像的主要问题已有更直接的标签读取证据，因此本轮没有增加这条更宽、尚待验证的入口，更没有把推断路径塞进连续已观察历史。

## 验证范围

规则独立对照实际使用本地安装的 **PokerKit 0.7.4**；查阅的 stable 文档当前显示 0.7.5。对照脚本验证 10 组情况：第三盲歧义、多人开池跟注歧义、第三盲 option、免费让牌、两次足额加注下界、同额终点隐藏多次加注、已记录加注后的被动漏帧、封顶跟注、短全下后加注权未重开、以及退款反例。

公开 Swift 测试 `LedgerPassiveGapTests` 覆盖多人 limp、call/fold、短筹码封顶、保持关闭的加注权、两帧与行动者要求、漏字段、金额不守恒、非法顺序、跨街、退款边界和搜索预算。独立对照脚本已整理为 `tools/audit_recovery_pokerkit.py`：在 Python 3.11+ 环境安装 `pokerkit==0.7.4`，直接运行并将标准输出保存为 JSON；不能使用关闭断言的 `python -O`。脚本不依赖私有截图或 Swift 规则引擎。原始实验日志仍保存在本地，不随公开仓库上传。这些规则测试不证明策略能击败人类，也不替代最新版本的整段录像重放。
